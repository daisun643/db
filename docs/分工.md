# 小组分工

本项目按“功能闭环”分工。每位成员负责自己的数据库字段、后端接口、前端入口和对应测试，最终要求每个模块都能独立演示一个完整流程。

## 一、共性要求

1. 每个成员按“数据库变更、后端接口、前端入口、接口测试”的闭环完成自己负责的功能。
2. 每个功能必须增加对应测试，测试需要覆盖正常流程、异常流程和必要的权限限制。
3. 不得为了通过测试而删除、绕过或随意修改既有测试；确需调整测试时，需要说明原因并同步相关负责人。
4. 修改公共能力前必须提前同步通知，包括登录鉴权、RBAC、信用分、通知、钱包、数据库公共表和公共 DTO。
5. 涉及状态流转的功能必须限制非法状态变化，例如帖子封禁后不能编辑、订单完成后不能继续留言。
6. 涉及金额、库存、信用分的功能必须保证数据一致性，并补充对应测试。
7. 前端页面需要提供可操作入口，不能只完成接口；页面风格尽量和现有页面保持一致。
8. 提交前必须在 Docker Compose 环境下完成自测，至少保证自己模块相关测试通过。
9. 每次提交应聚焦一个功能点，避免把无关格式化、重构和其他模块改动混在一起，并在 `docs/模块功能/<对应模块>.md` 记录现状以及 TODO。
10. 功能开发完成后推送到对应`指定分支`，再根据需要通过 PR 合并到上游分支。

## 三、分支管理

每个成员在对应指定分支上开发。更改完成后先推送到指定分支，由成员 10 或对应模块负责人验收；验收通过后，再通过 PR 合并到上游分支。 master 分支有 commit 保护无法直接推送提交需 PR。

| 成员 | 负责模块 | 指定分支名 |
|---|---|---|
| 成员 1 | 用户、账号与后台权限 | `feat/auth` |
| 成员 2 | 社交关系与私信 | `feat/social-message` |
| 成员 3 | 系统通知与事件推送 | `feat/notification` |
| 成员 4 | 论坛帖子与评论 | `feat/forum/post-comment` |
| 成员 5 | 论坛治理与检索 | `feat/forum/governance-search` |
| 成员 6 | 商品发布与库存控制 | `feat/market/product-stock` |
| 成员 7 | 订单交易与钱包 | `feat/market/order-wallet` |
| 成员 8 | 纠纷仲裁 | `feat/market/dispute` |
| 成员 9 | 举报与审核闭环 | `feat/report-audit` |
| 成员 10 | 部署、集成与验收 | `deploy` |

## 四、信用分接入分工

信用分系统不单独拆人负责，而是接入到对应业务模块。

| 场景 | 负责人 |
|---|---|
| 用户信用分字段、基础展示、管理员调整 | 成员 1 |
| 低信用限制发帖、评论 | 成员 4、成员 5 |
| 低信用限制发布商品、下单 | 成员 6、成员 7 |
| 纠纷失败方扣分 | 成员 8 |
| 举报成立后扣分 | 成员 9 |
| 信用分相关验收用例 | 成员 10 |

|---|---|
| 角色、权限、用户角色绑定基础能力 | 成员 1 |
| 普通用户登录态和接口鉴权 | 成员 1 |
| 论坛版主权限 | 成员 5 |
| 商品和订单管理权限 | 成员 6、成员 7 |
| 仲裁员权限 | 成员 8 |
| 举报审核员权限 | 成员 9 |
| 部署环境账号和验收账号初始化 | 成员 10 |
