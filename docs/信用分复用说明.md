# 信用分复用说明

本文档由成员一提供面向其他模块成员，说明当前项目中信用分能力的含义、后端复用方式、管理接口和接入注意事项。

## 1. 基本概念

信用分相关字段主要在 `User` 和 `CreditAdjustment` 两张表中。

`User` 中常用字段：

| 字段 | 含义 |
| --- | --- |
| `credit` | 当前信用分，用于限制发帖、评论、发布商品、下单等行为 |
| `totalCredit` | 历史累计正向积分，用于计算等级 |
| `userLevel` | 用户等级，由 `totalCredit` 计算得到 |

`CreditAdjustment` 中常用字段：

| 字段 | 含义 |
| --- | --- |
| `userId` | 被调整信用分的用户 |
| `description` | 调整原因 |
| `changePoints` | 实际变化值 |
| `beforeCredit` | 调整前信用分 |
| `afterCredit` | 调整后信用分 |
| `operatorId` | 操作人，可以为空 |
| `adjustTime` | 调整时间 |

重要区别：

- `credit` 是当前信用分，会被加分和扣分影响。
- `totalCredit` 只累计正向实际加分，用于等级成长；扣分不会降低 `totalCredit`。
- `userLevel` 根据 `totalCredit` 计算，只升不降。
- 当前信用分上下限为 `0` 到 `1000`。

## 2. 推荐后端复用方式

其他模块后端需要判断用户是否允许执行某个业务动作，或需要调整信用分时，优先复用 `ICreditService`。

命名空间：

```csharp
using Backend.Services;
```

在 Controller 或 Service 中通过构造函数注入：

```csharp
private readonly ICreditService _creditService;

public PostsController(ICreditService creditService)
{
    _creditService = creditService;
}
```

### 2.1 判断用户是否可执行操作

方法：

```csharp
Task<bool> CanPerformAsync(int userId, string operation);
```

当前已内置的 `operation`：

| operation | 最低信用分 | 建议使用场景 |
| --- | --- | --- |
| `post` | 60 | 发帖 |
| `comment` | 40 | 评论 |
| `product.publish` | 50 | 发布商品 |
| `order.create` | 50 | 下单 |
| 其他字符串 | 大于 0 | 临时兜底判断 |

示例：

```csharp
var canPost = await _creditService.CanPerformAsync(currentUserId, "post");
if (!canPost)
{
    return BadRequest(new { message = "当前信用分不足，无法发帖" });
}
```

建议：

- 成员 4、5：发帖、评论前调用 `post` 或 `comment`。
- 成员 6：发布商品前调用 `product.publish`。
- 成员 7：下单前调用 `order.create`。
- 如果需要新增业务动作阈值，先和成员 1 同步，再扩展 `CreditService.CanPerformAsync`。

### 2.2 调整信用分并记录流水

方法：

```csharp
Task<CreditAdjustment?> AdjustCreditAsync(
    int userId,
    int changePoints,
    string reason,
    int? operatorId = null);
```

参数含义：

| 参数 | 含义 |
| --- | --- |
| `userId` | 被调整信用分的用户 ID |
| `changePoints` | 调整分值，正数加分，负数扣分 |
| `reason` | 调整原因，会写入流水，最长保留 500 字符 |
| `operatorId` | 操作人 ID；系统自动任务或无法确定操作人时可以传 `null` |

返回值：

- 用户存在：返回本次 `CreditAdjustment` 流水。
- 用户不存在：返回 `null`。

示例：纠纷处理后扣减责任方信用分。

```csharp
var adjustment = await _creditService.AdjustCreditAsync(
    liableUserId,
    -20,
    $"纠纷 #{ticketId} 仲裁成立，扣减信用分",
    currentUserId);

if (adjustment == null)
{
    return NotFound(new { message = "用户不存在" });
}
```

示例：举报成立后扣减违规用户信用分。

```csharp
await _creditService.AdjustCreditAsync(
    reportedUserId,
    -10,
    $"举报 #{reportId} 审核成立，扣减信用分",
    reviewerUserId);
```

注意：

- 实际写入 `changePoints` 的是夹取上下限后的实际变化值。
- 例如用户当前信用分为 `5`，调用 `AdjustCreditAsync(userId, -20, ...)` 后，`afterCredit` 为 `0`，流水中的 `changePoints` 为 `-5`。
- 不要直接修改 `User.Credit`，否则不会生成流水，也不会维护等级积分。
- 不要直接插入 `CreditAdjustment`，除非你同时维护用户信用分字段；正常业务都应调用服务方法。

### 2.3 兼容旧方法

当前保留旧方法：

```csharp
Task AddCreditAsync(int userId, int credit, string reason);
```

该方法内部会调用 `AdjustCreditAsync(userId, credit, reason)`，但无法记录操作人。新业务建议使用 `AdjustCreditAsync`。

## 3. HTTP 接口

信用分 HTTP 接口前缀为：

```text
/api/user
```

鉴权方式：Cookie 登录态，登录后浏览器或测试客户端会自动携带 `TongjiForumAuth`。

### 3.1 查看用户信用分

```http
GET /api/user/{userId}/credit
```

权限规则：

- 用户可以查看自己的信用分。
- 管理员或具备 `users.view`、`users.edit`、`users.ban`、`dashboard.view` 任一权限的用户可以查看他人信用分。
- 未登录返回 `401`。
- 登录但无权查看他人信用分返回 `403`。

响应示例：

```json
{
  "userId": 4,
  "username": "user",
  "email": "4@tongji.edu.cn",
  "userLevel": 1,
  "totalCredit": 100,
  "credit": 100
}
```

### 3.2 查看当前用户信用流水

```http
GET /api/user/credit-adjustments
```

权限规则：

- 仅查看当前登录用户自己的最近 50 条信用流水。
- 未登录返回 `401`。

响应示例：

```json
[
  {
    "creditAdjustmentId": 12,
    "userId": 4,
    "description": "举报 #8 审核成立，扣减信用分",
    "changePoints": -10,
    "beforeCredit": 100,
    "afterCredit": 90,
    "operatorId": 1,
    "operatorName": "admin",
    "adjustTime": "2026-07-09T10:30:00"
  }
]
```

### 3.3 管理员查看指定用户信用流水

```http
GET /api/user/{userId}/credit-adjustments
```

需要权限：

```text
users.view 或 dashboard.view
```

返回指定用户最近 50 条信用流水。用户不存在时返回 `404`。

### 3.4 管理员调整信用分

```http
POST /api/user/credit/add
```

需要权限：

```text
users.edit 或 users.ban 或 dashboard.view
```

请求体：

```json
{
  "userId": 4,
  "credit": -10,
  "reason": "举报成立，扣减信用分"
}
```

字段说明：

| 字段 | 含义 |
| --- | --- |
| `userId` | 被调整用户 ID |
| `credit` | 调整分值，正数加分，负数扣分，不能为 0 |
| `reason` | 调整原因，不能为空 |

响应示例：

```json
{
  "message": "信用分调整成功",
  "adjustment": {
    "creditAdjustmentId": 15,
    "userId": 4,
    "description": "举报成立，扣减信用分",
    "changePoints": -10,
    "beforeCredit": 100,
    "afterCredit": 90,
    "operatorId": 1,
    "operatorName": "admin",
    "adjustTime": "2026-07-09T10:30:00"
  }
}
```

注意：

- 请求体中的 `operatorId` 即使传入也不应作为可信来源；后端会使用当前登录用户作为操作人。
- 业务模块内部扣分优先调用 `ICreditService.AdjustCreditAsync`，不要为了内部业务再走 HTTP 接口。

## 4. 前端入口

当前已有入口：

- 个人资料页：展示当前用户信用分、等级、总积分、信用流水。
- 管理员系统状态页：用户表中可查看用户信用分，并通过“调整”按钮打开弹窗进行加分或扣分。

如果其他模块前端只需要展示当前用户信用信息，建议优先使用：

- `/api/auth/me`
- `/api/user/profile`
- `/api/user/{userId}/credit`

如果是业务页面需要判断能否操作，建议由后端接口统一判断并返回明确错误信息，前端只负责展示错误提示。不要只在前端根据信用分隐藏按钮，因为用户可以绕过前端直接请求接口。

## 6. 测试建议

涉及信用分的模块至少覆盖：

1. 正常信用分用户可以执行业务操作。
2. 低信用分用户被拒绝，接口返回明确错误信息。
3. 业务扣分后，`User.credit` 发生变化。
4. 业务扣分后，`CreditAdjustment` 生成流水。
5. 流水包含原因、调整前后分值、实际变化值、操作人和时间。
6. 扣分到低于 `0` 时，最终信用分被限制为 `0`。
7. 加分到高于 `1000` 时，最终信用分被限制为 `1000`。
8. 普通用户不能调用管理员调分接口。

已有成员一测试文件可参考：

```text
test/tests/test_auth.py
```

其中 `TestStage6Credit` 覆盖了管理员查看、管理员调整、普通用户禁止调整、流水字段和上下限夹取。

## 7. 常见问题

### 为什么扣了信用分，等级没有下降？

等级由 `totalCredit` 决定，`totalCredit` 只累计正向实际加分。当前设计是等级成长不因扣分下降；扣分影响的是当前 `credit`。

### 为什么流水中的变化值和我传入的扣分值不同？

因为信用分有上下限。流水中的 `changePoints` 记录实际变化值，而不是原始请求值。

### 可以直接改数据库里的 `credit` 吗？

不建议。直接改 `credit` 不会生成流水，也不会记录操作人和原因。业务代码应使用 `ICreditService.AdjustCreditAsync`。

### 业务系统自动扣分时操作人怎么填？

如果是审核员、仲裁员等人工操作，传当前登录用户 ID。  
如果是系统自动任务，可以传 `null`，但 `reason` 必须写清楚来源，例如“系统自动检测重复违规，扣减信用分”。
