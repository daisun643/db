# 数据库触发器与存储过程

跨表不变式、派生字段、内容审核和资金状态机都在数据库内实现，脚本为 `database/08_triggers.sql`、`database/09_procedures.sql` 与 `database/10_views.sql`。应用层只保留授权判定、通知文案和响应组装。

## 1. 职责边界

| 规则 | 实现位置 |
| --- | --- |
| 帖子与评论的敏感词审核、审核记录 | `TRG_Post_Sensitive*`、`TRG_PostComment_Sensitive*` |
| 点赞数、浏览量等派生汇总 | `TRG_PostLike_Count`、`sp_post_view` |
| 新用户必有钱包、新版块必有版主 | `TRG_User_DefaultWallet`、`TRG_Forum_CreatorManager` |
| 通知已读时间、好友关系变更时间 | `TRG_Notification_ReadTime`、`TRG_FriendShip_TouchTime` |
| 订单终态归档留言板、库存归零锁定商品 | `TRG_Transaction_ArchiveMsg`、`TRG_Product_StockLock` |
| 信用分调整、钱包充值、下单、支付、收货、取消、纠纷结案 | 8 个 `sp_` 存储过程 |
| 资金流水的收入与支出口径 | 视图 `V_FinanceFlow` |
| 身份与资源授权、通知文案与 SSE 推送、分页排序、纠纷责任方的信用规则 | 仍在 Controller 与 Service |

保留在应用层的部分各有依赖：授权依赖 JWT 与 Permission Claim，通知推送依赖进程内的 SSE 连接，分页排序属于展示层。

## 2. 触发器（08_triggers.sql）

| 触发器 | 表与时机 | 数据库行为 | 应用层配合 |
| --- | --- | --- | --- |
| `TRG_Post_SensitiveStatus` | `Post` BEFORE INSERT OR UPDATE | 标题或正文命中敏感词时把 `status` 改写为 `PendingReview` | 写入时统一给 `Active`，返回前 `ReloadAsync()` |
| `TRG_Post_SensitiveAudit` | `Post` AFTER INSERT OR UPDATE | 命中时插入 `AuditRecord`（`targetType='Post'`、`status='Pending'`） | 不再手工补写审核记录 |
| `TRG_PostComment_SensitiveStatus` | `PostComment` BEFORE INSERT OR UPDATE OF `content` | 评论正文命中时改写为 `PendingReview` | 同上 |
| `TRG_PostComment_SensitiveAudit` | `PostComment` AFTER INSERT OR UPDATE OF `content` | 命中时插入 `AuditRecord`（`targetType='Comment'`） | 同上 |
| `TRG_PostLike_Count` | `PostLike` AFTER INSERT OR DELETE | `Post.likeCount` 原子加减，下限为 0 | 删除“读取-加一-回写”代码，返回前 `ReloadAsync()` |
| `TRG_User_DefaultWallet` | `User` AFTER INSERT | 为新用户插入零余额 `Wallet` | 注册流程不再建钱包 |
| `TRG_Forum_CreatorManager` | `Forum` AFTER INSERT | 把创建者写入 `ForumManager`，`role='Moderator'` | 创建后重查时 `Include(ForumManagers)` |
| `TRG_Notification_ReadTime` | `Notification` BEFORE UPDATE OF `isRead` | 翻转为已读写入 `readTime`，回退为未读时清空 | 不再手工赋 `ReadTime` |
| `TRG_FriendShip_TouchTime` | `FriendShip` BEFORE INSERT OR UPDATE | 统一刷新 `updateTime` | UPDATE 路径不再赋值；INSERT 仍需给初值，因为该列非空 |
| `TRG_Transaction_ArchiveMsg` | `Transaction` AFTER UPDATE OF `transactionStatus` | 订单进入 `Completed`/`Cancelled`/`Refunded` 时把留言置为 `isArchived='1'` | 已删除 `ArchiveOrderMessagesAsync` |
| `TRG_Product_StockLock` | `Product` BEFORE UPDATE OF `stock` | 库存小于等于 0 且商品为 `Active` 时改为 `Locked` | 不再拼接条件更新表达式 |

两点实现细节：`Post.content` 是 CLOB，Oracle 不允许出现在 `UPDATE OF` 子句中（ORA-25006），因此帖子触发器改用块内 `UPDATING('title') OR UPDATING('content')` 判定，只在内容真正写入时重新审核，避免置顶、封禁等纯状态变更把已审核的帖子打回待审。触发器体内不能 `COMMIT` 或 `ROLLBACK`。

敏感词表为 `PostSensitiveWord`，匹配函数 `fn_find_sensitive_word(p_title, p_content)` 做大小写不敏感的子串匹配，命中多个词时返回 `id` 最小的那个，保证审核结果可复现。

## 3. 函数与存储过程（09_procedures.sql）

`fn_ensure_wallet(p_user_id)` 返回用户钱包 ID，不存在则创建零余额钱包，供各存储过程复用，取代了应用层的 `GetOrCreateWalletAsync`。

通用约定：

- `p_code = 0` 表示成功，此时 `p_message` 为 NULL；非 0 时 `p_message` 是可直接返回前端的中文提示；
- 过程内只用 `SAVEPOINT` 与 `ROLLBACK TO` 做局部回滚，不 `COMMIT`，事务边界由调用方决定；
- 并发安全依赖 `SELECT ... FOR UPDATE` 加上带条件的 `UPDATE` 并检查 `SQL%ROWCOUNT`，不依赖“先读后判”。

| 过程 | 关键入参 | 关键出参 | 数据库内完成 |
| --- | --- | --- | --- |
| `sp_adjust_credit` | `p_user_id`、`p_change_points`、`p_reason`、`p_operator_id` | `p_before_credit`、`p_after_credit`、`p_real_change`、`p_adjustment_id` | 0~1000 夹取、更新 `User.credit`、写 `CreditAdjustment` 流水 |
| `sp_wallet_deposit` | `p_user_id`、`p_amount` | `p_code`、`p_message`、`p_balance`、`p_transaction_id` | 加余额并写入 `productId` 为空的 `Completed` 流水 |
| `sp_post_view` | `p_post_id` | `p_view_count` | 浏览量原子自增并回传最新值 |
| `sp_create_order` | `p_buyer_id`、`p_product_id` | `p_code`、`p_message`、`p_transaction_id`、`p_amount`、`p_product_title`、`p_seller_id` | 校验商品与自购、条件扣减库存、建 `Pending` 订单 |
| `sp_pay_order` | `p_transaction_id`、`p_buyer_id` | `p_code`、`p_message`、`p_balance`、`p_amount`、`p_seller_id` | `Pending → Paid`、余额条件扣款、写 `payTime` |
| `sp_confirm_receipt` | `p_transaction_id` | `p_code`、`p_message`、`p_amount`、`p_seller_id`、`p_seller_balance` | `Paid → Completed`、结算卖家钱包、售罄商品转 `Sold` |
| `sp_cancel_order` | `p_transaction_id` | `p_code`、`p_message` | `Pending → Cancelled`、回补库存并恢复商品为 `Active` |
| `sp_resolve_dispute` | `p_ticket_id`、`p_refund_amount`、`p_decision` | `p_code`、`p_message`、`p_transaction_id`、`p_final_status`、`p_buyer_id`、`p_seller_id`、`p_order_amount`、`p_seller_amount`、`p_buyer_wallet_id` | 工单转 `Resolved`、订单转 `Refunded` 或 `Completed`、买卖双方划款、写退款与结算流水、写 `ArbitrationResult` |

错误码属于接口契约，Controller 直接把 `p_message` 放进 `BadRequest` 响应体，修改文案时同步更新 `test/tests/` 的断言：

| 过程 | 非 0 `p_code` 与 `p_message` |
| --- | --- |
| `sp_wallet_deposit` | 1 充值金额必须大于 0；2 充值失败 |
| `sp_create_order` | 1 商品不可下单（不存在或非 `Active`）；2 不能购买自己发布的商品；3 库存不足或商品已锁定 |
| `sp_pay_order` | 1 当前订单不可支付；2 商品卖家不存在；3 钱包余额不足；4 订单不存在 |
| `sp_confirm_receipt` | 1 当前订单不可确认收货；2 商品卖家不存在；4 订单不存在 |
| `sp_cancel_order` | 1 只有待支付订单可以取消；4 订单不存在 |
| `sp_resolve_dispute` | 1 该纠纷已处理；2 订单当前不在纠纷处理中；3 退款金额不能超过订单金额；4 该纠纷或订单状态已变化，不能重复结算；5 纠纷不存在；6 订单或卖家不存在 |
| `sp_post_view`、`sp_adjust_credit` | 无 `p_code`。帖子不存在时 `p_view_count` 为 NULL；用户不存在时 `p_adjustment_id` 为 NULL，调用方按“调整记录为空”处理 |

`sp_resolve_dispute` 只负责资金与状态；纠纷对买卖双方信用分的影响仍由应用层按责任方规则调用 `sp_adjust_credit`，因为该规则与业务判定耦合，且需要写入通知。

## 4. 视图 V_FinanceFlow（10_views.sql）

一行代表某个用户的一笔收入或支出，由四段 `UNION ALL` 组成：

| 方向 | 来源 | `description` |
| --- | --- | --- |
| 支出 | 本人作为买家的商品订单，状态为 `Paid`/`Completed`/`Disputed`/`Refunded` | `购买商品：<标题>`；商品已下架时为 `订单消费（商品已下架）` |
| 收入 | 本人作为卖家的 `Completed` 订单 | `出售商品：<标题>` |
| 收入 | `productId` 为空的 `Completed` 流水，即钱包充值 | `钱包充值` |
| 收入 | `DisputeRefund`、`DisputeSettlement` 流水 | `纠纷退款`、`纠纷结算` |

`FinanceController` 通过 keyless 实体 `FinanceFlow` 读取（`HasNoKey()` 加 `ToView("V_FinanceFlow")`），只做按用户过滤、汇总和排序。冻结金额是 `flowType='支出' AND status='Paid'` 的合计，可用金额为钱包余额减去冻结金额。口径调整只改这一处 SQL。

## 5. 后端调用方式

统一通过 `backend/Data/OracleProcedure.cs`：

```csharp
var code = OracleProcedure.OutInt32("p_code");
var message = OracleProcedure.OutText("p_message");
await OracleProcedure.CallAsync(_db, "sp_pay_order",
    OracleProcedure.InInt32("p_transaction_id", id),
    OracleProcedure.InInt32("p_buyer_id", userId),
    code, message,
    OracleProcedure.OutDecimal("p_balance"),
    OracleProcedure.OutDecimal("p_amount"),
    OracleProcedure.OutInt32("p_seller_id"));

if (OracleProcedure.ReadInt32(code) != OracleProcedure.Success)
    return BadRequest(new { message = OracleProcedure.ReadText(message) ?? "当前订单不可支付" });
```

调用约定：

- `CallAsync` 复用 EF Core 的当前连接与事务（`GetDbConnection()` 与 `CurrentTransaction.GetDbTransaction()`），因此可以与 `SaveChangesAsync()` 处于同一事务边界；
- 命令文本拼装为 `BEGIN "sp_pay_order"(:p_transaction_id, ...); END;`，并设置 `OracleCommand.BindByName = true`。过程名必须带引号：对象是带引号创建的，不加引号会被 Oracle 大写成 `SP_PAY_ORDER` 而找不到；
- OUT 参数回传的是 ODP.NET 专有值类型（`NUMBER` 对应 `OracleDecimal`，`VARCHAR2` 对应 `OracleString`），它们不实现 `IConvertible`，必须用 `ReadInt32`、`ReadDecimal`、`ReadText` 拆箱，直接 `Convert.ToInt32` 会抛 `InvalidCastException`；
- EF Core 不感知触发器对 `:NEW` 的改写。凡是响应依赖触发器结果（帖子与评论状态、点赞数、浏览量、版块版主、好友时间）的接口，返回前要 `await _db.Entry(entity).ReloadAsync();` 或重新查询。

## 6. 变更与排错

- 修改触发器、过程或视图后，执行 `./scripts/restart.sh --reset-data --wait` 重建数据卷，或用 SQL*Plus 以 `appuser` 单独执行对应脚本；容器重启不会重跑初始化脚本；
- 三个脚本末尾都有校验块，对象未编译通过或数量不足时用 `RAISE_APPLICATION_ERROR` 让初始化直接失败：`-20801`/`-20802` 触发器、`-20901`/`-20902` 过程、`-21001` 视图；
- 新增对象后同步调整脚本末尾的数量阈值，并更新本文档与 `database/README.md` 的清单；
- PL/SQL 块内允许空行需要 `SET SQLBLANKLINES ON`；`WHENEVER SQLERROR EXIT SQL.SQLCODE` 必须写在校验块之前，否则块自身的错误也会中断脚本；
- 校验块必须查 `all_objects`、`all_triggers`、`all_procedures` 并按 `owner = 'APPUSER'` 过滤。容器初始化脚本是以 SYS 连接、靠 `ALTER SESSION SET CURRENT_SCHEMA = APPUSER` 切换模式执行的，对象属于 APPUSER 而 `user_*` 视图只看得到 SYS 自己的对象，用 `user_*` 会得出“对象数为 0”的错误结论。

定位无效对象：

```sql
SELECT object_name, object_type, status FROM all_objects
 WHERE owner = 'APPUSER' AND status <> 'VALID';
SHOW ERRORS PROCEDURE "sp_create_order";
```
